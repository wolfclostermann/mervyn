# Handoff — Slack → Telegram, and GFS decoupling

*Written 2026-09-16. Covers the state of the project after the transport switch, the
operational knowledge that is not obvious from the code, and what is still outstanding.*

---

## What changed and why

Mervyn's chat transport was a Slack bot installed in the **GFS Engineering** workspace, which
tied a personal assistant to a company tenancy. Slack cannot be decoupled from that without
standing up a separate workspace; Telegram needs no workspace at all and has first-party
desktop, web and mobile clients on one account.

The bot is now **`@wc_mervyn_bot`** on Telegram, reached by **long polling** (`getUpdates`).

The structural consequence is bigger than a transport swap: **Mervyn has no inbound surface any
more.** Gone are the `/slack/events` route, HMAC signature verification, the ngrok tunnel and
its reserved domain. The VPS makes outbound connections only. The axum server still runs, but
serves just `/health` and the optional admin route, and is not publicly reachable.

Separately, the GFS decoupling is complete: the Slack app was removed from the GFS workspace
and its tokens verified dead, the GCP deploy path (`gcp-stack/`, `scripts/deploy-gcp.sh`) was
removed because it depended on GFS's private Terraform modules, and every remaining credential
is personal.

## Architecture

```
tokio task ──getUpdates(offset, timeout=30)──> api.telegram.org
             └─ allowlist ─ ingest ─ dedupe ─ filter ─ classify ─ dispatch ─ sendMessage
```

| Concern | Where |
|---|---|
| API client, chunking, 429 backoff | `src/telegram/client.rs` |
| Long-poll loop, cursor | `src/telegram/poller.rs` |
| Allowlist, filter ladder, dedupe | `src/telegram/handler.rs` |
| Wire types | `src/telegram/updates.rs` |
| Delivery log | `src/storage/message_ingest.rs` |
| Dedupe claims + poll cursor | `src/storage/meta.rs` |

Everything downstream of the transport was already transport-agnostic and did not change:
the eight intent handlers, the context assembler, the Claude client, vault sync, the scheduler.

## Things that will bite you

**Authorization is a single chat id, and it is the only thing protecting the bot.**
Long polling has no transport-level authentication — unlike Slack's signing secret, nothing
stops a stranger who discovers the bot's username from messaging it. `TELEGRAM_CHAT_ID` is an
allowlist of exactly one chat, checked in `telegram/handler.rs` **before** any database write
and **before** any Claude call, so an unknown sender cannot grow the database or spend quota.
Unauthorised updates are logged at `warn` and dropped. Do not weaken this without replacing it.

**Production runs under *root's* podman store.** `podman ps` as `opc` reports the container as
absent or exited, which reads as "the service is down" when it is perfectly healthy. Always:

```sh
sudo podman ps
sudo podman logs mervyn_mervyn_1
```

**The vault's `worklog.md` symlink is *meant* to look broken from the host.** It points at
`/worklog/worklog.md`, the path where `docker-compose.yml` bind-mounts the clone *inside the
container*. `/worklog` does not exist on the host. Pointing it at a host path breaks the sync
silently: `sync.rs` checks `worklog_path.exists()`, which follows the dead link and returns
false, so the worklog is skipped and every tick logs `worklog_entries: 0` — indistinguishable
from "nothing changed". This happened for months and was masked by the assembler's fallback to
the `worklog_git` mirror, so prompts still had worklog content while the database had none.

**Obsidian is two-way as of 2026-09-17** (`docs/two-way-vault-sync.md`). It used to be strictly
one-way, Markdown → redb, with rows keyed by FNV content hash — so editing a line in Obsidian
minted a new id and left the original row orphaned, and a chat-created event never appeared in the
vault at all. Items now carry their id in the file as an HTML comment (`<!--mv:1a2b-->`), and a
snapshot table records what the two sides last agreed on, which is what lets sync tell a human's
edit from the scheduler's own change.

The vault is also a git clone now, pushed to a private repo so a laptop and a phone can hold it
(`[vault_git]`, and Obsidian Git at the other end — Obsidian Sync has no headless client and cannot
reach a server). `worklog.md` is an ordinary file in it.

The direction that bites: **write-back ships disabled**. `[vault] write_back_enabled = false`, so
until it is switched on the behaviour is the old import and nothing is written. Turn it on with
`MERVYN__VAULT__WRITE_BACK_ENABLED=true`; the first write of each run backs the managed files up
to a timestamped sibling of the vault. `worklog.md` is deliberately excluded — it is a symlink
into the worklog clone, and modifying that working tree would break `git pull --ff-only`.

**`podman restart` does not re-read `.env`.** It reuses the environment the container was created
with, so changing `~/mervyn/.env` and restarting looks like it worked and changes nothing. Use
`sudo /usr/local/bin/podman-compose up -d --force-recreate` from `~/mervyn` (the full path matters:
`sudo` drops `/usr/local/bin` from `PATH` on this box), or just redeploy. Non-secret settings belong
in the compose `environment:` block, which is part of the deployed bundle, rather than in `.env`.

**A deploy used to be able to report success and ship nothing.** `podman-compose up -d` treats
an already-running container as satisfied, so a freshly loaded `:deploy` tag never reached it.
`scripts/deploy-remote-setup.sh` now passes `--force-recreate` and then verifies the running
container's image id matches the tag, failing loudly if not. Both halves are needed; the verify
step is the backstop. **Do not trust a deploy's exit code alone** — look for:

```
[deploy-remote-setup] verified: container <id> runs mervyn:deploy (<image>)
```

**The Telegram bot token travels in the URL path** (`https://api.telegram.org/bot<TOKEN>/...`),
which is Telegram's design, not a choice here. It is inside TLS so it is not exposed on the
wire, but it must never reach a log: `reqwest` errors embed the URL, so every error from the
client is mapped through `without_url()`. `TelegramClient` deliberately does not derive `Debug`,
and `Secrets` implements `Debug` with the values redacted. If it ever leaks, `/revoke` in
BotFather reissues instantly.

## Operating it

**Deploy** (builds arm64 locally, copies the image, recreates the container):

```sh
./scripts/deploy-oci.sh --local-build --use-local-env opc@132.145.17.140
```

`--use-local-env` uploads `./.env`. The alternative decrypts `.env.enc` and prompts for a
passphrase (`scripts/env-crypto.sh`); keep that blob refreshed when secrets change.

**Health.** There is no public URL. Check `sudo podman logs mervyn_mervyn_1`, or
`curl localhost:3000/health` on the box — which only started working on 2026-09-17, when a
`127.0.0.1:3000:3000` mapping was added to Compose. Before that the port was published nowhere and
this instruction was wrong. A healthy start looks like:

```
telegram bot authenticated bot=wc_mervyn_bot
telegram startup greeting sent
telegram poller started offset=Some(...)
```

`offset=None` on a start that is **not** the first means the cursor was lost and old messages
may be reprocessed.

**Required environment** (`.env`, see `.env.example`): `ANTHROPIC_API_KEY`,
`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. All three are rejected if present-but-empty, so a
half-filled file fails at startup rather than midway through the poll loop. Optional:
`MERVYN_ADMIN_TOKEN` (enables `GET /admin/message-ingest`), `MERVYN_WORKLOG_GITHUB_PAT`.

**Getting a chat id**: DM the bot, then read `message.chat.id` from
`https://api.telegram.org/bot<TOKEN>/getUpdates`. Do it *before* the first run — the poller
consumes pending updates and advances the cursor.

## Delivery semantics

The cursor is both acknowledgement and replay guard: `getUpdates` with an `offset` above an
`update_id` confirms it server-side. It is persisted in `META_TABLE` and advances **per batch,
after handling**, so a crash mid-batch redelivers — which is why each update is still claimed
for dedupe in `meta::try_claim_delivery`. A poisoned update cannot wedge the loop, because the
batch advances whether individual updates succeeded or not; failures land as `Failed` rows in
the ingest log.

Replies are chunked at 4096 UTF-16 units (Telegram's cap; an emoji is one char but two units)
and sent as plain text with **no `parse_mode`** — Claude's output is Markdown-ish and would
otherwise need `MarkdownV2` escaping on every stray character. 429s honour
`parameters.retry_after`, capped at 60s.

Updates are processed **serially**, so a slow Claude call delays the message behind it.

## Known gaps

- `docs/code-audit-fix-list.md` — 19 items. Item 4 (vault/id collisions) is fixed by the id
  markers, and item 1 (reminder consistency) is addressed as far as it can be: the send cannot be
  made transactional, but one failure no longer aborts the tick and repeat announcements are
  bounded. One P0 stands: appointment reminders scan the whole events table every tick
  (`scheduler/appointment_reminders.rs`).
- ~~The worklog pull is disabled pending a rework.~~ **Done 2026-09-17:** the worklog moved into
  the vault repo, `[worklog_git]` became `[vault_git]`, and the sync runs both ways. The separate
  clone, the `/worklog` mount and the symlink are all gone.
- ~~No way to browse stored data.~~ **Done 2026-09-17:** `/admin/events`, `/admin/reminders`,
  `/admin/todos` and `/admin/vault` read the tables directly. redb takes an exclusive lock, so a
  second process cannot open the file while Mervyn runs — before these, diagnosing "is it actually
  in the database?" meant stopping to copy `mervyn.redb` off the box.
- **No conversation memory.** Each message is classified and dispatched independently, so
  "add that to my calendar" referring to a previous message cannot work.
- **No edit path in chat.** The intents are add/remove only; correcting an event from chat means
  remove then re-add. Editing the line in Obsidian now works, once write-back is enabled.
- `retry_num` in `message_ingest` is vestigial — it modelled Slack's retry header and is always
  `None` under Telegram, but is still returned by the admin endpoint.
- Non-text messages (photos, stickers) are filtered as `FilteredNonText`. A screenshot of an
  appointment will not work; forwarded **text** does.
- `future_integrations.md` and `code-audit-fix-list.md` still reference Slack.
